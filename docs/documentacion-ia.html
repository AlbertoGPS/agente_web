Chat vs Agente — La diferencia fundamental

Chat simple

Usuario escribe → modelo responde → fin. El modelo solo genera texto. No ejecuta acciones. Un turno, una respuesta.

Agente

Usuario da un objetivo → modelo planifica → ejecuta herramientas → evalúa → decide si continúa o termina. Múltiples pasos autónomos.

flowchart LR subgraph CHAT["Chat simple"] U1[Usuario] -->|mensaje| M1[Modelo] M1 -->|respuesta| U1 end subgraph AGENTE["Agente"] U2[Usuario] -->|objetivo| M2[Modelo] M2 -->|tool call| T1[Backend] T1 -->|resultado| M2 M2 -->|¿necesito más?| M2 M2 -->|respuesta final| U2 end style CHAT fill:#450a0a,stroke:#ef4444 style AGENTE fill:#14532d,stroke:#22c55e

El loop agéntico en tu código

// gemini_agent.js — el corazón del agente
let response = await textChat.sendMessage({ message: text });

// El modelo decide cuántas veces necesita herramientas
while (response.functionCalls?.length > 0) {
    // Ejecuta todas las tools en paralelo
    const results = await Promise.all(
        response.functionCalls.map(llamada => ejecutarHerramienta(llamada.name, llamada.args))
    );
    // Devuelve resultados al modelo para que decida qué sigue
    response = await textChat.sendMessage({ message: results });
}
// Cuando no hay más function calls → respuesta final al usuario

Patrón Universal Router

En vez de definir una función por endpoint (N tools = N definiciones en código), se define una sola tool genérica. El modelo aprende los endpoints desde el prompt, no desde el código.

Enfoque clásico — N tools

Agregar endpoint = modificar código + agregar función + redesplegar. El programador es el cuello de botella.

Universal Router — 1 tool

Agregar endpoint = actualizar base.md. Sin tocar código. El modelo aprende del prompt.

flowchart TD USER[Usuario] --> MODEL[Modelo Gemini] MODEL -->|"consultar_backend\n{intencion: 'getAllAssets'\nparametros: '{}'}"| ROUTER[Universal Router\napi.js] ROUTER -->|despacha según intencion| BACK[Backend RedGPS] BACK --> ROUTER ROUTER --> MODEL MODEL --> USER PROMPT[base.md\nCatálogo de endpoints] -.->|conocimiento| MODEL style ROUTER fill:#1e3a5f,stroke:#4f6ef7 style PROMPT fill:#22263a,stroke:#4f6ef7,stroke-dasharray: 5

Definición de la tool — una sola para todo

// prompt.js — UNA tool que maneja todos los endpoints
export const herramientas = [{

    function: {

            required: ['intencion', 'parametros']

Economía de Tokens — Límites y Costos

Gemini 2.5 Flash tiene una ventana de contexto de 1 millón de tokens. Cada vehículo típico ocupa ~300 tokens en JSON.

ActivosTokens aprox.¿Cabe en contexto?Costo por consultaVeredicto

Caso real RedGPS El cliente más grande tiene 12,000 activos — 3.6× el límite del contexto. Mandar todos los activos al modelo es técnicamente imposible, no solo ineficiente.

Fenómeno "Lost in the Middle"

Estrategia de Caché + Filtros del lado del servidor

Solución al problema de los 12,000 activos: el modelo nunca recibe todos los datos. Solo recibe el resultado de una consulta ya filtrada.

sequenceDiagram actor U as Usuario participant M as Modelo participant C as Caché JS participant B as Backend RedGPS U->>M: "¿Cuántos Toyota tengo en Zona Norte?" M->>C: consultar_cache({marca:"Toyota", grupo:"Zona Norte"}) alt Caché fresco (< 5 min) C-->>M: 47 vehículos filtrados else Caché vencido C->>B: getAllAssets() B-->>C: 12,000 vehículos (actualiza caché) C-->>M: 47 vehículos filtrados end M-->>U: "Tienes 47 Toyota en Zona Norte"

Implementación del caché con TTL

// En api.js — caché con tiempo de vida
let cache = null;
let cacheTimestamp = 0;
const CACHE_TTL = 5 * 60 * 1000; // 5 minutos

async function consultarCache(filtros = {}) {
    const ahora = Date.now();

    // Si el caché está vencido o no existe, refresca
    if (!cache || (ahora - cacheTimestamp) > CACHE_TTL) {
        cache = await fetchAllAssets();
        cacheTimestamp = ahora;
    }

    // Filtra localmente — el modelo solo recibe el resultado
    return filtrarActivos(cache, filtros);
}

function filtrarActivos(activos, { marca, modelo, grupo, estado }) {
    return activos.filter(v => {
        if (marca  && v.marca  !== marca)  return false;
        if (modelo && v.modelo !== modelo) return false;
        if (grupo  && v.grupo  !== grupo)  return false;
        if (estado && v.estado !== estado) return false;
        return true;
    });
}
Principio clave El modelo es bueno para razonar sobre datos, no para almacenarlos. El caché almacena, el modelo razona. Nunca deben invertirse los roles.

Normalización de Campos

Distintos endpoints del backend pueden retornar el mismo dato con nombres diferentes, lo que confunde al modelo al encadenar llamadas.

ConceptoEndpoint AEndpoint BEndpoint CCampo canónico
ID GPSimeiidgpsgpsIdidgps
PlacaplacapatentelicensePlateplaca
NombrenombrenamevehicleNamenombre

Normalizador en api.js

// Mapa de aliases → nombre canónico
const FIELD_MAP = {
    imei:         'idgps',
    gpsId:        'idgps',
    patente:      'placa',
    licensePlate: 'placa',
    name:         'nombre',
    vehicleName:  'nombre',
};

function normalizeResponse(data) {
    if (Array.isArray(data)) return data.map(normalizeResponse);
    if (typeof data !== 'object' || data === null) return data;

    return Object.fromEntries(
        Object.entries(data).map(([k, v]) => [
            FIELD_MAP[k] ?? k,   // mapea si existe alias, si no conserva
            normalizeResponse(v) // recursivo para objetos anidados
        ])
    );
}

// Aplicar en el despachador, antes de devolver al modelo
const raw = await postRedGPS(endpoint, body);
return normalizeResponse(raw); // el modelo siempre ve campos consistentes

RAG — Retrieval Augmented Generation

RAG permite que el modelo responda sobre grandes volúmenes de información sin necesidad de cargar todo en el contexto. Se basa en buscar primero, enviar solo lo relevante.

flowchart TD subgraph FASE1["Fase 1 — Indexación (se hace una vez)"] D1[Documento 1] --> E[Modelo de\nEmbeddings] D2[Documento 2] --> E D3["... 10,000 docs"] --> E E --> VDB[(Vector DB\nPinecone / pgvector\nChromaDB)] end subgraph FASE2["Fase 2 — Consulta (en tiempo real)"] Q[Pregunta del\nusuario] --> EQ[Embedding\nde la pregunta] EQ --> SEARCH[Búsqueda\nde similitud] VDB --> SEARCH SEARCH --> TOP["Top 5-10\ndocumentos relevantes\n(texto plano)"] TOP --> LLM[Modelo LLM] LLM --> ANS[Respuesta] end style FASE1 fill:#1a1d27,stroke:#4f6ef7 style FASE2 fill:#1a1d27,stroke:#22c55e
Los embeddings son solo para buscar — el modelo recibe texto plano Un embedding es un vector numérico [0.23, -0.87, 0.41...] que representa el significado semántico. Se usa para encontrar qué es relevante. El modelo nunca ve los vectores — siempre recibe el texto original de los documentos encontrados.

Cuándo aplicar RAG en tu caso

SituaciónSolución recomendada
Datos operativos en tiempo real (posición GPS, ignición)Caché + filtros
Datos que cambian cada horas (activos, grupos)Caché TTL + filtros
Documentos estáticos (manuales, políticas, FAQs)RAG
Historial extenso de recorridos / reportesRAG o consulta paginada

¿Qué es el Asistente de RedGPS?

🤖

Un asistente inteligente para tu flota

Es un sistema que entiende preguntas en lenguaje natural y las traduce en consultas a tu plataforma de rastreo. En lugar de navegar menús, simplemente preguntas.

Analogía: Imagina que tienes un asistente humano que conoce perfectamente tu plataforma de rastreo. Le dices "¿cuántos vehículos Toyota tengo en la Zona Norte?" y él consulta el sistema, agrupa los datos y te responde. El asistente de IA hace exactamente eso, pero de forma automática.
2

¿Cómo entiende mis preguntas?

💬

No es un chat normal

Un chat normal solo responde con lo que ya sabe. El asistente de RedGPS puede ir a buscar información a tu plataforma, procesarla y darte una respuesta con datos reales.

Ejemplo paso a paso

3

¿Por qué el asistente no puede ver todos mis vehículos a la vez?

🧠

La IA tiene una "memoria de trabajo" limitada

Piensa en la IA como una persona que puede trabajar con cierta cantidad de información a la vez en su escritorio. Si pones demasiados papeles, ya no puede procesar bien.

Analogía del escritorio: Un analista muy capaz puede revisar 50 expedientes con detalle y darte un análisis perfecto. Si le mandas 12,000 expedientes de golpe, su escritorio colapsa — físicamente no caben. La solución no es buscar un analista más grande, sino enviarle solo los expedientes relevantes para cada consulta.

❌ Lo que no se puede hacer

Enviar los 12,000 vehículos completos al asistente en cada pregunta. No caben en su "escritorio de trabajo" y el costo sería prohibitivo.

✅ Cómo se resuelve

El sistema filtra primero en el servidor y solo envía al asistente la información relevante para esa consulta específica.

¿Qué es el caché y por qué ayuda?

⚡

Una memoria temporal que evita consultas repetidas

El caché guarda temporalmente la lista de vehículos en el navegador. Así, si haces varias preguntas seguidas, no se tiene que pedir la lista al servidor cada vez.

Analogía: Es como imprimir el directorio telefónico una vez y tenerlo en tu escritorio. Cuando alguien te pida un teléfono, lo buscas en tu copia local en segundos. Solo vuelves a imprimir cuando el directorio cambia. Cada 5 minutos el sistema verifica si hay cambios y actualiza si es necesario.

¿Cómo funciona con documentos y manuales?

📚

Busca antes de responder

Cuando el asistente necesita información de documentos (manuales, políticas, reportes históricos), no los lee todos. Primero busca cuáles son relevantes para tu pregunta, y solo esos los revisa.

Analogía de la biblioteca: Imagina una biblioteca con 10,000 libros. Cuando le preguntas al bibliotecario sobre "procedimientos de mantenimiento preventivo", no lee los 10,000 libros — va al índice, encuentra los 3 libros relevantes, los lee y te responde. El sistema de índice inteligente se llama RAG.

Preguntas que usa el caché

Estado actual de vehículos, posiciones, ignición, grupos — datos que cambian frecuentemente.

Preguntas que usan RAG

Manuales de uso, políticas de la empresa, reportes históricos, documentación técnica — datos estáticos o que cambian poco.
